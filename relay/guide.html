The guide

How Ghost Chat works

Two browsers, one code, no accounts and no server that can read a word. This page walks through every piece: what runs where, how your browsers find each other on any network, how the keys are made, and what happens to a message between your keyboard and their screen.

01 · Tech stack

Built from browser standards, not frameworks

Ghost Chat is a static web page. There's no backend of its own, no build-time framework and no CDN: every line of code that runs is served from this site, and the only network connections the page is allowed to make are listed in its Content-Security-Policy.

Interface

Plain HTML, CSS, JavaScript

ES modules with no framework. Every piece of text from the other person goes into the page as text, never parsed as HTML.

Crypto

Web Crypto API

The browser's own audited primitives: AES-256-GCM, ECDH P-384, HKDF and HMAC with SHA-384. The one-time ECDH private key is created non-extractable.

Post-quantum

ML-KEM-1024

NIST's FIPS 203 standard, via the vendored @noble/post-quantum 0.7.1. Combined with ECDH, so breaking one is not enough.

Transport

WebRTC DataChannel

A direct, DTLS-encrypted pipe between the two browsers when the network allows it. STUN servers help each side find its public address.

Signaling

PeerJS 1.5.5

The public PeerJS server introduces the two browsers so WebRTC can start. It passes connection details, never keys or messages.

Relay

Cloudflare Worker

A WebSocket relay on a Durable Object (free plan). Used when a direct link is impossible: VPNs, mobile data, strict NAT. It forwards sealed bytes.

Sharing

QR codes, Web Share

The invite is drawn as a QR code locally (vendored uqr), or handed to your phone's share sheet. The secret part of the link never reaches a server.

Quality

Tests and a deterministic build

node --test for the protocol, Playwright driving real Chromium browsers for end-to-end runs, and a single-file build with a hashed CSP.

02 · The big picture

Who is involved in one conversation

Two browsers do all the work. Two helper servers exist only so they can find each other and, when the network gets in the way, pass sealed packets along. Neither helper ever holds a key.

03 · The room code

Twenty characters: a name and a secret

When you start a chat, your browser draws 100 random bits and writes them as 20 characters (no 0/O or 1/I to misread). The first five name the room on the introduction server. The other fifteen, 75 bits of secret, never leave the two browsers.

Room key

The full code is stretched with HKDF into a 384-bit room key. It salts the handshake, so only someone holding all 20 characters can prove themselves.

Relay room

On the relay, the room is named by a 128-bit hash of the room key. The relay can't reverse it, and can't link it to the public room name.

Expiry

An unused code expires after 10 minutes (you can extend it to an hour). Once someone joins, the code stops working altogether: the room locks.

04 · Connecting

Finding each other on any network

Direct connections are fastest but many networks block them. Ghost Chat tries direct first and, if nothing has opened after two and a half seconds (or the attempt fails), dials the relay at the same time. Whichever pipe opens first carries the handshake. Pick a situation to follow its path.

05 · Handshake

Three messages, two key exchanges, one proof

The handshake does three jobs at once: it agrees on fresh keys (twice, with two unrelated kinds of math), it proves both sides hold the room code, and it produces a safety number you can compare by voice.

Why two exchanges

ECDH P-384 is battle-tested; ML-KEM-1024 resists quantum computers. The session key needs both secrets, so an attacker must break both.

Why the proof

The introduction server could try to sit in the middle. Without the 15 secret characters it can't produce a valid HMAC, and the connection is refused.

Why the safety number

If someone saw the code before your friend joined, they could get in first. Comparing the 60 digits by voice rules that out.

06 · A message's journey

From your keyboard to their screen

Every message, read receipt, reaction and typing signal goes through the same pipeline. The receiving browser runs it backwards and checks everything on the way.

  1. You type“meet at ten”Text stays in memory only.
  2. Packaged{t:"msg", mid, text}A small JSON object with a random 64-bit id.
  3. Padded256 BRounded up to 256 B, 1 KB, 4 KB, 16 KB or 64 KB, so length gives little away.
  4. New keykey #42The ratchet turns once: a fresh AES key, used once, then deleted.
  5. Sealed9f3a…c1e7AES-256-GCM. The message counter is bound in, so replays and reordering are caught.
  6. Sentdirect or relayThe transport only ever carries this sealed frame.
If anything is off, the chat ends. A frame that fails authentication, arrives twice, out of order or with a skipped counter closes the connection instead of being shown. Silence is safer than a forged message.
07 · Files

Files travel the same way, and never open by themselves

A file is cut into 60 KB pieces. Each piece is padded to 64 KB and sealed with its own message key, exactly like a text message, and checked for completeness at the end. Up to 100 MB per file.

1 · Recognise

The real type is read from the file's first bytes, not from its name or the sender's claim.

2 · Hold

Nothing is shown or played automatically. Photos appear only when you press View, and only PNG, JPEG, GIF or WebP.

3 · Warn

Programs, scripts, installers and documents with macros are flagged, and saving them asks first.

4 · Save safely

Saved as plain bytes under a cleaned name, so the browser can't render or run them on the way.

08 · Lifecycle & panic

From first hello to nothing left

Waiting for a join→ Handshake→ Locked & chatting⇄ Reconnecting→ Ended & wiped

Reconnecting

If the network drops, the browsers retry for up to three minutes. The returning side must prove the resume secret, so the safety number stays the same and nobody new can slip in.

Ending

When one side ends the session or closes the tab, it sends an authenticated goodbye: a random token it handed over inside the encrypted channel. The other side ends at once.

Panic wipe

The panic button (or Esc three times) sends the goodbye, blanks the page, clears the clipboard, drops every key and leaves for another site. On phones you hold it briefly so a stray tap can't trigger it.

What a wipe can't reach. Screenshots, copies the other person keeps, and anything malware on a device has already seen. Ghost Chat stores nothing, but it can't un-see for someone else.
09 · Code map

Separate engines, one small page

The code is split into modules with one job each. The crypto never touches the page, the interface never touches a key, and every transport is just a pipe for bytes that are already sealed.

10 · FAQ

Questions people ask

Can I add a third person to a chat?

Not into the same room. Each room's keys and safety number belong to one pair, and it locks once both are in. To talk to someone else, use "New room for someone else" in the session panel: it opens a separate private room in a new tab. True group rooms need a bigger protocol (keys and safety numbers for every pair) and aren't built yet.

Does it work with a VPN, on mobile data or at work?

Yes. If a direct link can't open, Ghost Chat uses the relay over an ordinary HTTPS WebSocket on port 443, which those networks allow. The relay only sees sealed bytes.

Are my messages saved anywhere?

No. Not on a server, and not in your browser: there are no cookies, no localStorage, no IndexedDB. Close the tab and they're gone on your side.

Can the other person see my IP address?

On a direct link, yes, as with any peer-to-peer call. Choose Maximum privacy before connecting to go through the relay instead; then only the relay sees it.

What can I do with a message after sending it?

Edit it (the other side sees it marked "edited"), delete it for both of you, or delete it only from your screen. Only the author can edit or delete for both; the other browser checks that.

How do I know the page itself wasn't tampered with?

You're trusting whoever serves the page, as with any web app. The build prints a SHA-256 of the single-file version; you can rebuild it from the source and compare, or host that file yourself.
